# 压测笔记（benchmark）

> 详细数据与复现步骤见 `docs/performance.md`；这里只记结论和踩过的坑。

## 结论（同机 loopback、1KB 回显）

| 配置 | 客户端 | QPS |
|------|--------|-----|
| 0~1 IO 线程（单线程服务端） | 1 线程 / 100 连接 | 9.3–9.5 万 |
| 2 IO 线程 | 8 线程 / 800 连接 | ~11.8 万 |
| 4 IO 线程 | 8 线程 / 800 连接 | ~22 万 |
| 8 IO 线程 | 8 线程 / 800 连接 | 32–34 万 |
| 8 IO 线程 | 16 线程 / 1600 连接 | 37 万（瓶颈回到客户端） |
| 8 IO 线程、1000 连接 | 8 线程 / 1000 连接 | 32.3 万 |
| 8 IO 线程、60s 长稳 | 8 线程 / 800 连接 | 32.7 万（0 错误，约 2.5 核） |

> ⚠️ 只有第一行是「客户端 1 线程」测的，**不能和下面几行算倍数**：
> 同一个单线程服务端放在 8 线程客户端下只有约 5.8 万（过压），
> 所以 9.5 万 → 33.5 万不是 3.5 倍。

每请求服务端 CPU：15–25 µs（`getrusage` 前后差值 / 请求数）。

## 三个坑

1. **客户端饱和**：原报告 8 线程 18 万，其实是 4 个客户端线程的上限；客户端加到 8/16 线程后服务端到 32–37 万。压测第一步是证明客户端不是瓶颈。
2. **batch RTT**：`-b 100` 时 P50/P99 是“100 条一批”的总延迟，单条 ≈ P50/batch；写进报告/简历要换算或标注。
3. **0.11% vs 38%**：组内 0.11% 来自脚本“服务端只启动一次、组间不重启”，是热重复，不代表跨进程噪声；真实跨进程波动 7–18%。

## 与参考实现对比

- 参考 echo 示例每条消息一行 `LOG_INFO`，同步写日志把 io=8 拖到 24.6–25.2 万；
- 去掉日志、用当前源码重编后 31.2–33.2 万，与 my-muduo 的 30.6–33.6 万持平（差 <1%）；
- 参考仓库的 `build-rel` 比源码旧，对比前必须重编。

## 压测客户端自身的 5 轮审计（2026-10-28）

完整审查在 `benchmarks/BENCH_CLIENT_REVIEW.md`。压测工具本身被连审 5 轮，每轮都能找出新问题，
说明「测量工具也要被测量」。

| 版本 | 问题 | 修法 |
|---|---|---|
| v1 | `payload` 无上限 / 负数 → `bad_alloc`；`port` 超 65535 静默截断 | 严格 `strtoll` + 范围校验（1..1MiB / 1..65535） |
| v1 | 阻塞 `connect`：对端不回 SYN 要等内核约 2 分钟 | 非阻塞 `connect` + `poll(5s)` + `getsockopt(SO_ERROR)` |
| v1 | `timeout` 和真错误混成一个数；一条连接失败拖垮整线程 | `IoResult` 分类；失败 fd 摘掉，其余连接继续 |
| v2 | `messages=1e8` + `reserve` = 每线程 800MB | 上限降到 1e6；`reserve(min(messages, cap))` |
| v2 | 多连接时把「整轮 RTT」当成「单条延迟」 | 输出标注 `rtt` / `batch`，README 说明不可横向比较 |
| v3/v4 | 没有连接数维度；成功率口径偏高；`attempted` 记计划数 | 加 `--connections`；`connected` 挪到 warmup 后；`attempted` 循环内累加 |
| v5 | `--duration` 被 `messages` 静默截断；退出码 2 会中断脚本；样本截断不吭声 | duration 模式忽略 messages；退出码 0/1/2/3；输出 `capped` |

三条通用教训：

- 工具的边界参数（0、负数、超大值）和失败模式（不可达、服务端 `SIGSTOP`）要和功能一样测；
- 输出必须带口径标签，否则「batch RTT」一定会被读成「单条延迟」；
- 两个限制条件（`--duration` 与 `messages`）不能同时生效，必须有明确优先级；
  压测脚本的退出码也是接口的一部分。
