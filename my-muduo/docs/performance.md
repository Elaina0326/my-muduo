# 性能测试报告

> **这份报告里每个 QPS 都绑定客户端配置。** 不附「客户端线程数 / 连接数」的绝对 QPS 没有意义——
> 同一个服务端，只把客户端从 1 线程改成 8 线程，就能让测出来的 QPS 差 39%（见 §5）。

## 0. 摘要

单机 loopback、1 KB 回显，固定客户端（8 线程 / 800 连接 / 每轮 100 条）：

| 服务端 IO 线程 | QPS | 每 IO 线程 QPS |
|---|---|---|
| 1（过压对照） | 58,368 | 58.4k |
| 2 | 117,532 | 58.8k |
| 4 | 220,418 | 55.1k |
| 8 | **334,988** | **41.9k** |

**每 IO 线程吞吐在 4 线程以内稳定在 55–59k，8 线程降到 42k（−24%）。** 也就是说 2–4 线程是近线性扩展，8 线程开始出现资源争用。

## 1. 环境

| 项 | 值 |
|---|---|
| CPU | AMD Ryzen 9 7940HX，16 核 / 32 线程 |
| 系统 | Ubuntu 26.04 on WSL2，kernel 6.18.33.2-microsoft-standard-WSL2 |
| 编译器 | g++ 15.2.0 |
| 构建 | Release（`-O2 -DNDEBUG`） |
| 拓扑 | loopback（客户端与服务端同机，**不是**跨机测量） |
| 负载 | 1 KB 定长回显，1000 条/连接 |
| 频率调节 | 不可读（WSL2 无 cpufreq），CPU 降频不受控 |

环境快照见 `benchmarks/results/2026-10-29/`。`ulimit -n` 在脚本内提到 100000。

## 2. 怎么复现

```bash
cmake -S . -B build-rel -DCMAKE_BUILD_TYPE=Release
cmake --build build-rel -j$(nproc)

# 固定客户端配置，只扫服务端 IO 线程数（约 4 分钟）
bash benchmarks/run_server_scaling.sh
```

单组手跑：

```bash
./build-rel/echo_server_mt 8888 4 &
./build-rel/bench_client 127.0.0.1 8888 8 1000 1024 --connections 800
```

`bench_client` 参数顺序是 `host port 客户端线程数 每连接消息数 [payload] [--connections N] [--duration S]`。

## 3. 服务端 IO 线程扩展

**固定条件**：客户端 8 线程 / 800 连接 / batch = 800÷8 = 100 条每轮 / 1 KB。
**每档 5 次，每次重启服务端，取中位数。**

| 服务端 IO | QPS 中位 | 范围 | 每 IO 线程 QPS | P99 batch | 单条 P99 约 |
|---|---|---|---|---|---|
| 0 * | 58,256 | 57,050 – 64,464 | 58.3k | 26.7 ms | 267 µs |
| 1 * | 58,368 | 50,000 – 67,759 | 58.4k | 26.3 ms | 263 µs |
| 2 | 117,532 | 110,137 – 133,801 | 58.8k | 12.6 ms | 126 µs |
| 4 | 220,418 | 217,788 – 223,925 | 55.1k | 5.7 ms | 57 µs |
| 8 | 334,988 | 325,747 – 372,058 | 41.9k | 3.0 ms | 30 µs |

\* `io=0/1` 这两档是 **8 个客户端线程压 1 个服务端 loop** 的过压对照，不代表服务端在单线程下的能力上限（那是 9.5 万，见 §5）。

**三个观察：**

1. **`io=0` 与 `io=1` 相差 0.2%**（58,256 vs 58,368）。0 个 IO 线程意味着全部在 base loop 处理，1 个 IO 线程意味着全部在一个子 loop 处理——两者都只有一个线程做 IO，结果一致符合预期。**这是对测量链路最好的自洽性校验。**
2. **2 线程每线程 58.8k，和单线程的 58.4k 持平**，说明 2 线程区间没有额外开销。
3. **8 线程每线程 41.9k，比 4 线程的 55.1k 低 24%**，边际效率降到约 72%。

**`io=1` 那档范围是 50.0–67.8k（35% 波动），中位数不稳。** 其余档位波动在 2.8%–14%。所有档位之间的差距（1.9×）都远超组内波动，结论不受影响。

## 4. 为什么这里没有"加速比"

报告不给 `8 线程 = 单线程的 N 倍` 这样的数字，因为**不存在一个对所有档位都公平的基数**：

| 测法 | 单线程服务端 | 8 线程服务端 | 问题 |
|---|---|---|---|
| 客户端 1 线程 / 100 连接 | 95,487（干净） | 喂不满，测不出 | 客户端在 8 线程时成为瓶颈 |
| 客户端 8 线程 / 800 连接 | 58,256（**被过压**） | 334,988（干净） | 单线程时客户端过度施压 |

两种配置各自在某一端失真。把它们拼起来算倍数，等于拿"被压低的基数"去除"正常的上限"，会得到虚高的 5.75 倍；反过来用 95,487 作基数，又混进了另一套客户端配置。

**所以本报告只给「每 IO 线程吞吐」这一列**——它不需要基数，也不会因为客户端配置变化而失去意义。

## 5. 客户端线程数本身是显著变量

同一服务端（`echo_server_mt 8888 0`，单线程处理 IO）：

| 客户端配置 | QPS | 说明 |
|---|---|---|
| 1 线程 / 100 连接 | **95,487** | 客户端不干扰服务端 |
| 8 线程 / 800 连接 | **58,256** | 客户端过压，服务端 QPS 掉 39% |

同一份服务端代码、同样的 1 KB 消息，**唯一的变量是客户端**。

**这不是 CPU 争抢**——绑核实验（服务端 `taskset -c 0`、客户端 `taskset -c 2-31`）后 QPS 仍为 58,071，与不绑核的 58,728 相差 1.1%。物理核已经隔开，差异没有消失。

**结论：压测客户端的配置是测量的一部分，不是背景。** 任何横向对比都必须固定客户端线程数与连接数。

## 6. 连接数与消息大小

> ⚠️ 以下为 **2026-10-28 单次采样**，服务端 4 IO 线程、客户端 4 线程。样本只有 1 次，
> 跨进程波动 7–18%，**只能作定性结论**，不能和 §3 的数字横向比较（客户端配置不同）。

### 连接数（4 IO 线程 / 1 KB）

| 连接数 | QPS | 单条成本 | P99 batch |
|---|---|---|---|
| 10 | 51,154 | 32.1 µs | 352 µs |
| 100 | 177,203 | 17.7 µs | 1,123 µs |
| **500** | **216,782** | **15.4 µs** | 3,226 µs |
| 1000 | 180,158 | 20.1 µs | 9,411 µs |

500 条连接是拐点。1000 条时吞吐掉 17%，但 **P99 从 3.2 ms 涨到 9.4 ms（2.9 倍）**——延迟的恶化比吞吐更明显，说明超出临界点后排队开始主导尾延迟。

### 消息大小（4 IO 线程 / 100 连接）

| 大小 | QPS | 吞吐 | 单条成本 |
|---|---|---|---|
| 64 B | 177,181 | 10.8 MB/s | 17.8 µs |
| 1 KB | 168,395 | 164 MB/s | 17.9 µs |
| 16 KB | 144,987 | 2.26 GB/s | 27.4 µs |
| 64 KB | 83,693 | **5.22 GB/s** | 44.6 µs |

小包时每条消息的固定开销（约 17.8 µs）占主导；64 KB 时固定开销被摊薄，吞吐接近 loopback 的内存拷贝速率（5.22 GB/s）。

> 64 KB 那行的 P999 实测 42,517 µs，**不可信**——只有 500 轮样本，P999 相当于第 0.5 个样本。样本量不足时不要引用 P99 以上的分位数。

## 7. 测量方法：三条踩过的坑

这一节比数字本身更重要。

**① 客户端线程数是显著变量**

客户端 1 → 8 线程，同一服务端 QPS 掉 39%。已用绑核实验排除 CPU 争抢（§5）。**任何对比都必须固定客户端配置。**

**② "组内波动 0.11%" 是假精度**

第一版脚本让服务端只启动一次、组内连跑 3 次，测出极差 0.11%，一度以为精度很高。实际上那测的是**同一进程热重跑**（缓存热、分配器热、连接对象复用 free list）。

改成每次重启后，同一配置的组内波动是 **3.4%–7.6%**。跨进程的真实波动还有 7–18%（同一配置在不同时间跑出 165k / 177k / 180k）。

**判读规则**：效应小于 10–20% 不下结论。

**③ P99 必须标注 batch 大小**

多连接模式下输出的 P99 是 **batch RTT**（一轮 N 条的总时间），不是单条延迟。之前曾出现"线程越多 P99 越低"的误读——其实是因为 `batch = 连接数 / 线程数` 从 100 降到了 12.5，一轮变短了。换算成单条后趋势相反（267 µs → 30 µs 才是真实改善方向，在固定 batch 后测得）。

**判读规则**：跨行比较 P99 前，先确认 batch 相同。

## 8. 性能分析工具速查

```bash
# 找热点函数（WSL2 里内核可能没编 perf 事件，先跑一次确认可用）
perf record -g -F 999 ./build-rel/echo_server_mt 8888 4
perf report

# IPC / cache miss / 上下文切换
perf stat -p $(pgrep -x echo_server_mt)

# 数系统调用——排查"客户端效应"时用它看 EAGAIN 和 epoll_ctl 次数
strace -c -f -p $(pgrep -x echo_server_mt)

# 锁竞争
perf lock record ./build-rel/echo_server_mt 8888 4

# 连接状态与发送队列：send-q 持续非零说明服务端发不出去
ss -tnp | grep 8888 | head

# fd 数量：验证 800 连接是否真的建起来了
ls /proc/$(pgrep -x echo_server_mt)/fd | wc -l

# 线程数：验证 setThreadNum 是否生效
ls /proc/$(pgrep -x echo_server_mt)/task | wc -l

# 分离用户态/内核态 CPU：判断"谁在干活"
awk '{print "utime=" $14 " stime=" $15}' /proc/$(pgrep -x echo_server_mt)/stat
```

> WSL2 下 `perf` 不一定可用（取决于内核是否编译了 perf 事件支持），
> `strace`、`ss`、`/proc` 一定可用。本项目实际只依赖后三者。
>
> 最后一条（分离 utime/stime）是区分"服务端多干活"和"服务端被饿着"的关键：
> 被抢占的进程 CPU 时间会**减少**，多干活的才会**增加**。§5 的结论就是靠这个方向判定的。

## 9. 局限

- **同机测量**：客户端与服务端抢占同一台机器的 CPU、缓存、内存带宽，所有数字是**端到端上限**，不是服务端的理论容量。
- **`io=0/1` 两档被客户端过压**，不能当作单线程服务端能力（真实值是 95,487）。
- **未记录服务端 CPU/请求**：因此无法给出"每请求成本"。补这一列才能把"客户端效应"和"服务端效率"彻底分开。
- **CPU 频率不受控**：WSL2 读不到 cpufreq governor，降频会造成额外的组间波动。
- **固定消息数而非固定时长**：5000 条在高吞吐下只跑 2–3 秒，可能未进入稳态。`--duration` 模式下同配置的每条成本比固定轮数低约 20%，说明短跑有启动开销。
- **P99 以上的分位数在样本不足时不可信**（见 §6 的 64 KB 行）。
- **压测不能开 Sanitizer**：ASan / TSan 会让性能下降数倍。正确做法是功能正确性用 sanitizer 验证，性能用干净的 Release 构建测。
- **大消息 + 多连接会超时**：64 KB 消息在 100 连接 × 1000 条/连接下会撞上客户端的 `SO_RCVTIMEO`（5 秒），必须减少连接数或每连接条数。

## 10. 对外口径

**可以写：**

> 单机 loopback、1 KB 回显：服务端 8 个 IO 线程、客户端 8 线程 / 800 连接时达到 33.5 万 QPS（P99 3.0 ms）；每 IO 线程吞吐在 4 线程以内稳定在 55–59k，8 线程降到 42k。

**不要写：**

- ❌「8 线程是单线程的 5.75 倍」——基数取的是被客户端过压的档位
- ❌「单线程 5.8 万」——那是 8 线程客户端压 1 个服务端的结果，不是能力上限
- ❌ 任何不附「客户端线程数 / 连接数」的绝对 QPS
- ❌ 把不同客户端配置的数字拼成一条"扩展曲线"
